# Architecture and API

One Go process serves the embedded Vite SPA, `/api/v1`, deployment/DNS/certificate/notification workers, and the metrics scheduler. PostgreSQL holds typed resource metadata, encrypted secrets and release snapshots, sessions, roles, jobs, domain ownership, events and metrics. No Docker API or SSH agent is exposed publicly.

Native Linux installations use a local Docker transport instead of SSH for their automatically registered Local host. Both transports implement command execution, file transfer, forwarded TCP/Unix connections and container terminals. Docker exec/attach communicates with a host-networked executor; it exposes no network endpoint. The installation records and verifies the daemon identity before running workers. Protected system resources describe the control-plane ingress reservation and dashboard routes outside projects. They share proxy generation, DNS ownership and certificate renewal with applications, while cleanup and terminal authorization exclude them.

`GET/PUT /settings/dashboard-access` and `/retry` are administrator-only. A protected route reserves the exact dashboard hostname before HTTP-01 issuance. HAProxy forwards only syntactically valid challenge requests for configured dashboard hosts to the expiring-token handler. Public dashboard access requires a valid certificate. A hostname change preserves the previous route until issuance, proxy validation and HTTPS verification succeed. Effective-origin helpers centralize cookies, CSRF, invitations, Git callbacks and WebSocket authorization. No loopback setup listener or confirmation flow exists. Encrypted backups include settings, identity, certificate material and reservations. `local-host verify` explicitly acknowledges an independently checked Docker identity after restoration.

The version-change coordinator operates outside paused deployment workers. A protected detached container using the currently installed executor runs preflight, maintenance/drain, encrypted backup, transactional schema migration, component replacement and HTTPS verification. Its database record and root-only, atomically synced host journal support resumption. Only non-destructive reverse migrations permit automatic recovery; other failures retain maintenance mode and the backup. See [release operations](releases.md).

Resources follow team → project → environment → application → route. Servers, Docker networks, Git connections and DNS zones are platform infrastructure with explicit team grants. Platform administrators manage infrastructure and backups; team owners manage memberships and projects; project operators configure/deploy/roll back and open container terminals; viewers have read access without secret values. Local sessions require CSRF headers for mutations; streams enforce the same project permissions.

Jobs are claimed with `FOR UPDATE SKIP LOCKED`, have renewable leases and durable stages, and serialize application operations with advisory locks. Source commits are fetched in the control plane and archived to the host. Builds and Compose execution occur over verified SSH connections. Releases retain local image identities. HAProxy configuration is generated from stored route records, validated in a candidate container, persisted, and gracefully reloaded. Workloads continue running independently of the control plane.

HTTPS/gRPC dispatch uses persisted exact-host and ordered wildcard-regex maps, with a separate redirect map tied to the selected backend. Request paths are never rewritten. Configuration, maps and certificates are staged, validated and recovered together under the per-server proxy lock. Each normalized hostname identifies one web route; exact matches precede the longest wildcard suffix. TCP remains port-based. Legacy non-root path routes are removed only by the explicit cleanup command.

Guided Git setup stores encrypted, session-bound single-use state in PostgreSQL settings and uses administrator-only callbacks. Session cookies use SameSite=Lax for top-level provider redirects; mutations retain CSRF and Origin checks. GitHub manifest credentials and Gitea OAuth tokens use the resource vault. Gitea instance client secrets are encrypted separately in settings, and refresh rotation is serialized by connection. OAuth requests read:user/read:repository only; there is no remote Gitea webhook management. Generated signing secrets are returned once by an explicit authenticated mutation, then remain write-only. Setup configuration and status are documented in OpenAPI.

Builds, operational tasks, and metrics use separate worker lanes. A dropped SSH connection retries the prepared release using its pinned image IDs. Encrypted releases identify exact images, per-service network settings and per-container reserved IPv4/IPv6 addresses. HAProxy runs with host networking and targets those bridge IPs directly; backend ports are not published. Metrics reconcile actual container addresses under application locks and withdraw invalid targets. HAProxy reloads are acknowledged through its Unix runtime socket before a deployment becomes active. Its socket belongs to the SSH user and is accessible only inside the managed private directory.

HAProxy frontend binding overrides live in server-scoped `haproxy:<server-id>` entries in PostgreSQL settings. `web` identifies the HTTP redirect/HTTPS/gRPC frontend; TCP frontends use their route resource IDs. Absent overrides inherit all IPv4 interfaces and, when configured, IPv6. The administrator-only `GET/PUT /servers/{id}/haproxy` API exposes revisions, effective/default addresses, and durable apply status. A settings job shares the server's proxy lock with deployments, validates against the exact HAProxy 3.4 runtime image, and commits a revision only after the remote generation is acknowledged. Failed applies retain the committed settings; interrupted workers are retried through job leases. A persistent remote pending marker recovers the prior configuration and certificates before another update can replace its backup. These PostgreSQL settings are included in backups.

Certificates are scoped to the ACME directory as well as the DNS zone/domain. Changing from staging to production schedules replacement certificates even when the staging certificate is far from expiry. A failed renewal keeps the currently valid certificate available.

The API contract is [openapi.yaml](../api/openapi.yaml). Generate TypeScript types with `cd web && bun run api:generate`. Credentials are supplied only through the `secrets` property when creating/updating resources. Omitted keys are retained; an explicitly empty secret string removes a key. Ordinary runtime values use a separate plaintext `variables` map with `env:` or `preview-env:` keys; strings set values (including empty strings), `null` deletes, and omitted keys are retained. Setting either type removes the opposite type at the same key; conflicting writes in one request are rejected. BuildKit scopes remain secrets. Resource updates require the current `version`; kind, team and parent cannot be changed.

Remote-server removal uses administrator-only `POST /servers/{id}/deletion-plan`, `DELETE /servers/{id}`, `GET /servers/{id}/deletion`, `POST /servers/{id}/deletion/retry` and `PUT /servers/{id}/deletion/connection`. The generic resource-delete endpoint uses the same reviewed approval contract. Settings retain an expiring inventory and a durable `server-deletion:<id>` operation; workers serialize with application, preview, server, network and proxy operations. The resource-tree transaction freezes references before queuing cleanup, while a shared version-operation lock prevents overlap with system updates. Completed operations and audits remain readable after the server is gone. See [cleanup and recovery](recovery.md#deleting-a-remote-server).

Application/environment secret namespaces: `env:NAME`, `build:NAME`, `preview-env:NAME`, `preview-build:NAME`. Integration keys: `private_key`, `token`, `webhook_secret`; applications optionally use `registry_password`. Servers select `authMethod: private_key` (the default) or `password`, with the matching credential in encrypted `secrets.private_key` or `secrets.password`. Host fingerprints are verified before authentication for both methods. GitHub and SSH keys are distinct credentials. Runtime configuration is resolved and encrypted in each deployment snapshot.

Applications default to `source: git` (also used when omitted). Direct Compose applications use `source: compose`, `engine: compose`, `context: .`, `file: compose.yaml`, and supply YAML through encrypted `secrets.compose` when creating or configuring them. Git fields, auto-deploy and previews must be disabled. Operator-only `GET/PUT /applications/{id}/compose` returns/saves `{yaml, version}` with optimistic revision checks; public resource responses never contain the document. `POST /applications/{id}/deploy` accepts an optional expected `version` and rejects stale revisions with 409. Queueing freezes YAML in the encrypted deployment snapshot, then transfers only `compose.yaml` over SSH, bypassing Git. Source revisions are displayed as `compose:<content hash>`. The existing Compose build/pull, image pinning, health gates, stable project volumes and retained-release rollback paths are shared with Git deployments.

`GET /zones/{id}/certificates` returns public certificate metadata and renewal state for routes the caller can access, after checking access to the zone. It does not return PEM bundles or private keys. The dashboard links each domain from `/dns` to `/dns/{id}`, with separate records and certificates tabs.

SSE deployment streams are `/deployments/{id}/events`, supporting Last-Event-ID. Runtime logs are `/applications/{id}/logs?container=...`. Container terminal WebSockets use `/applications/{id}/terminal?container=...&csrf=...`, require an exact allowed Origin, and support JSON `data`/`resize` input with binary terminal output. Terminal content is not recorded; opening a terminal is audited.

Fresh deployment requests use `POST /applications/{id}/deploy` with `{fresh: true, confirmName, version}`. Name and current resource version are mandatory for this mode. The encrypted deployment snapshot freezes the mode; `fresh-deployment:<deployment-id>` settings record Docker identity, reset inventory and write-ahead volume-removal progress. Preparation and preflight precede teardown. After reset begins, failure keeps runtime stopped rather than automatically restoring the prior release. Pending reset recovery blocks other application mutations from replacing its inventory.

`DELETE /deployments/{id}` requires application write access and returns `202 {jobId}` for completed inactive deployments. Active releases, unfinished deployments and pending rollback targets return 409. A resource-tree transaction reserves the release against rollback; `deployment-delete` jobs share the application operation lock. `deployment-deletion:<id>` settings survive failures, and deployment responses expose optional `deleting`/`deletionError` fields. Repeating DELETE resumes failed cleanup. Cleanup targets release-specific containers/tags and unused files, preserves data and shared resources, then atomically removes release/history records and records completion. An inactive Compose release never triggers project-wide teardown.
